# API

## Общие правила

В стандартном Compose auth доступен на `http://localhost:8001`, resume — на `http://localhost:8002`. Через Vite на `http://localhost:5173` те же пути проксируются в нужный сервис. Префикса `/api` нет.

Swagger и OpenAPI: `/docs` и `/openapi.json` на каждом API-сервисе. Внутренние методы находятся в OpenAPI resume-сервиса, но требуют отдельного worker token.

Для защищённых публичных методов:

```http
Authorization: Bearer <access_token>
```

JSON-запросы передаются с `Content-Type: application/json`. Исключение — загрузка резюме через multipart. UUID и даты сериализуются строками. Владелец определяется по JWT, поле `user_id` не нужно передавать при создании ресурса.

| Код | Обычное значение |
| --- | --- |
| 200 | Чтение, вход, refresh или внутреннее обновление |
| 201 | Ресурс создан |
| 400 | Бизнес-ошибка, например повтор имени пользователя |
| 401 | Нет подходящей авторизации |
| 403 | Недостаточно прав сотрудника |
| 404 | Ресурс отсутствует или принадлежит другому пользователю |
| 409 | Недопустимый переход состояния адаптации |
| 422 | Запрос не соответствует схеме либо файл резюме не прошёл проверку |
| 500 | Необработанная ошибка сервиса |
| 503 | На сервере не настроен токен внутреннего API |

Стандартные HTTPException возвращают JSON `{"detail":"..."}`. Ошибки валидации имеют список в `detail`. Не следует считать, что любой 500 содержит JSON или означает, что POST ничего не сохранил.

## Авторизация

| Метод | Путь | Доступ | Ответ |
| --- | --- | --- | --- |
| POST | `/auth/register` | Без токена | 201: `user_id`, `username` |
| POST | `/auth/login` | Без токена | 200: access/refresh tokens |
| POST | `/auth/refresh` | Refresh token в теле | 200: access/refresh tokens |
| GET | `/auth/me` | Access token | `user_id`, `username`, `is_staff` |
| GET | `/auth/users` | Сотрудник | Массив пользователей |
| GET | `/auth/users/{user_id}` | Сотрудник | Пользователь |

Регистрация и вход принимают одинаковую форму:

```json
{
  "username": "candidate",
  "password": "example-password"
}
```

У схем пока нет правил сложности пароля и длины этих строк. Повторное имя возвращает 400; неверный пароль или неактивный пользователь при входе — 401.

Успешный вход или refresh:

```json
{
  "access_token": "<access_token>",
  "refresh_token": "<refresh_token>",
  "token_type": "bearer"
}
```

Refresh принимает `{"refresh_token":"<refresh_token>"}`. Сроки access/refresh — 15 минут / 30 дней, сейчас заданы в коде. Обработчик не нормализует все ошибки refresh: недействительный refresh token может дать 500. Клиент должен завершить сессию при неудачном обновлении.

Пользователь из `/auth/users` имеет `user_id`, `username`, `is_active`, `is_staff`. Регистрация не предоставляет выбор роли сотрудника. Методов изменения роли и серверного logout/revoke в этом API нет.

## Оригиналы резюме

Все методы требуют access token.

### POST `/resumes`

Multipart-поле `file` с PDF или DOCX. Файл проверяется по содержимому; пустые и некорректные файлы, а также зашифрованные PDF отклоняются с 422. OCR и отдельный публичный лимит размера файла не реализованы.

Успех: **201 с пустым телом**, а не JSON. Заголовок `Location` содержит URL `/resumes/{id}` для скачивания. Клиенту следует извлечь проверенный путь и обращаться к своему API: origin в абсолютном Location может относиться к внутреннему proxy.

Пример запроса curl из PowerShell после установки `$env:RESUME_ACCESS_TOKEN` в текущем процессе:

```powershell
curl.exe -i http://localhost:8002/resumes -H "Authorization: Bearer $env:RESUME_ACCESS_TOKEN" -F "file=@resume.pdf"
```

### GET `/resumes`

Список метаданных оригиналов текущего пользователя:

```json
[
  {
    "id": "11111111-1111-4111-8111-111111111111",
    "user_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
    "file_url": "http://minio:9000/resumes/example.pdf",
    "embedding": null,
    "created_at": "2026-11-04T10:00:00Z"
  }
]
```

`file_url` — внутренний адрес хранения, его не следует показывать как ссылку пользователю. `embedding` появляется после фоновой обработки и может оставаться `null`; это не блокирует создание адаптации.

### GET `/resumes/{resume_id}`

Возвращает **байты исходного документа** с Content-Type и `Content-Disposition: attachment; filename*=UTF-8''...`. Для отсутствующего или чужого оригинала — 404. Для браузерного скачивания нужен авторизованный fetch с Blob, а не ссылка с JWT в query.

## Вакансии

Все методы требуют access token.

| Метод | Путь | Ответ |
| --- | --- | --- |
| POST | `/vacancies` | 201: сохранённая вакансия |
| GET | `/vacancies` | Массив своих вакансий |
| GET | `/vacancies/{vacancy_id}` | Одна своя вакансия; чужая/отсутствующая — 404 |

Создание принимает полный текст:

```json
{
  "text": "Python Backend Developer\nFastAPI, PostgreSQL, автоматические тесты."
}
```

Ответ:

```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "user_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "text": "Python Backend Developer\nFastAPI, PostgreSQL, автоматические тесты.",
  "embedding": null
}
```

Frontend не отправляет пустой текст и ограничивает его 10 000 символами. Сама request-схема API содержит `text: str` без таких валидаторов, а столбец БД ограничен 10 000 символами. Нельзя рассчитывать на единообразный 422 для пустой или слишком длинной вакансии при прямом вызове API.

## Адаптации

### POST `/adaptations`

Требует access token и ровно два поля; дополнительные поля запрещены:

```json
{
  "resume_id": "11111111-1111-4111-8111-111111111111",
  "vacancy_id": "22222222-2222-4222-8222-222222222222"
}
```

Оба ресурса должны принадлежать текущему пользователю. При отсутствии или чужом владельце любого из них — 404. POST не запускает LLM внутри HTTP-запроса: он сохраняет `pending` и событие для worker в одной транзакции.

Ответ 201, `Location: /adaptations/33333333-3333-4333-8333-333333333333`:

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "user_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "resume_id": "11111111-1111-4111-8111-111111111111",
  "vacancy_id": "22222222-2222-4222-8222-222222222222",
  "status": "pending",
  "result": null,
  "error": null,
  "created_at": "2026-11-04T10:01:00Z"
}
```

Повтор того же POST создаёт новую задачу. После таймаута/сетевого сбоя/5xx нельзя автоматически повторять отправку: предыдущая запись могла сохраниться.

### GET `/adaptations/{adaptation_id}`

Требует access token, возвращает ту же форму с актуальным статусом. Чужая или отсутствующая задача — 404. Интерфейс использует polling раз в две секунды.

У завершённой задачи `status="done"`, `error=null`, а `result` имеет вид:

```json
{
  "resume_text": "Адаптированный текст резюме...",
  "review": {
    "passed": true,
    "issues": []
  }
}
```

При замечаниях Critic статус тоже `done`:

```json
{
  "resume_text": "Текст, требующий проверки...",
  "review": {
    "passed": false,
    "issues": ["В исходном резюме не подтверждено руководство командой."]
  }
}
```

При технической ошибке `status="failed"`, `result=null`, `error` содержит название класса исключения, например `ReadTimeout`. Тексты документов и ответ провайдера в это поле не записываются.

Допустимые переходы: `pending → running → done|failed`. Автоматического повторного запуска нет. Для новой попытки создаётся новая адаптация для сохранённых оригинала и вакансии.

**GET `/adaptations` отсутствует.** Общую историю задач получить нельзя; frontend хранит известные ID в памяти вкладки. Также отсутствуют публичные PATCH/DELETE ресурсов и экспорт адаптированного PDF/DOCX.

## Внутренний API worker

Базовый сервис — resume. Каждый метод требует заголовок:

```http
X-Worker-Token: <worker_token>
```

Также нужен query-параметр `user_id=<UUID>`; он проверяется по владельцу ресурса. JWT пользователя здесь не заменяет worker token. При неверном/отсутствующем токене — 401, при ненастроенном токене сервера — 503. Отсутствующий или чужой ресурс — 404.

| Метод | Путь | Тело | Результат |
| --- | --- | --- | --- |
| GET | `/internal/resumes/{id}` | — | Байты оригинала и Content-Disposition |
| GET | `/internal/vacancies/{id}` | — | Объект вакансии |
| GET | `/internal/resumes/{id}/embedding` | — | Массив чисел или `null` |
| GET | `/internal/vacancies/{id}/embedding` | — | Массив чисел или `null` |
| PATCH | `/internal/resumes/{id}` | `{"embedding":[0.1,0.2]}` или `{"embedding":null}` | Метаданные резюме |
| PATCH | `/internal/vacancies/{id}` | Та же форма embedding | Объект вакансии |
| POST | `/internal/adaptations/{id}/claim` | — | Задача в `running` или JSON `null` |
| PATCH | `/internal/adaptations/{id}` | Результат обработки | Обновлённая задача |

Claim атомарно меняет только `pending → running`. Для существующей задачи в любом другом статусе возвращает 200 с JSON `null`; это сигнал пропустить дубликат, а не повторить LLM.

Finish принимает одну из двух форм:

```json
{
  "status": "done",
  "result": {
    "resume_text": "Полный адаптированный текст",
    "review": {"passed": true, "issues": []}
  },
  "error": null
}
```

```json
{
  "status": "failed",
  "result": null,
  "error": "ReadTimeout"
}
```

Обновление возможно только из `running`, иначе 409. Для `done` обязателен результат и запрещена ошибка, для `failed` — наоборот. `resume_text` и `error` при наличии должны содержать непробельные символы. `review.passed` — строгий bool: true требует пустые `issues`, false — непустые; пустые замечания запрещены. Несогласованное тело или дополнительные поля — 422.

## Минимальный порядок вызовов

1. `/auth/register`, затем `/auth/login` и `/auth/me`.
2. Загрузить оригинал через `POST /resumes`, получить ID из Location или списка `GET /resumes`.
3. Сохранить полный текст через `POST /vacancies`, получить ID из JSON.
4. Передать оба ID в `POST /adaptations`, сохранить ID задачи и ссылку на результат.
5. Опросить `GET /adaptations/{id}` до `done` или `failed`.
6. При `done` отдельно проверить `review.passed` и прочитать `issues`.

Внутренние методы вызываются worker; интеграция браузера использует только публичный API.
